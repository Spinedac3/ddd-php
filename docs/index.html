Qué es un LLM — el paper de 2017

«Attention Is All You Need» (Google, 2017) es la arquitectura de todos los LLM actuales: el Transformer. Nació para traducir; terminó leyéndose internet. Vamos por partes:

La unidad con la que el modelo lee y escribe. No ve letras ni palabras: ve tokens — pedazos de texto de unos ¾ de palabra («desarrollador» pueden ser dos o tres), convertidos en números.

El contexto, el costo de cada consulta y la salida del modelo se miden en tokens.

Una red neuronal que convierte una secuencia de tokens en la predicción del siguiente. Los tokens entran como vectores de números, atraviesan decenas de bloques idénticos — cada uno aplica la atención del tab anterior más una red pequeña — y a la salida hay una probabilidad para cada token posible: se elige uno y se repite. No tiene memoria: re-lee el contexto completo para cada token que produce. Todos los LLM de hoy — GPT, Claude, Gemini — son variantes de este diseño.

Una búsqueda blanda en un diccionario. Para producir cada token, el modelo deja que cada palabra le «pregunte» a todas las demás cuánto importan (Q pregunta, K indexa, V aporta el contenido), y combina las respuestas con pesos que suman exactamente 1.

Ese «suman 1» importa: la atención es un presupuesto fijo. Todo lo que entra al contexto compite por él — cada cosa de más le cobra atención a la tarea. Vamos a volver a esto cuando hablemos de qué se le pasa al agente y qué no.

Porque fue la primera arquitectura que se pudo entrenar a lo grande. Los modelos anteriores leían en orden: para procesar la palabra 10 había que terminar la 9 — imposible de repartir entre miles de GPUs. El Transformer mira todo el contexto a la vez, así que el entrenamiento se reparte completo.

Misma receta, más máquinas, más texto → mejor modelo. Esa escalera es la que llevó de un traductor de 2017 a los LLM de hoy: no ganó por ser más listo con poco — ganó por ser el único que podía comerse internet.

OP 010Para arrancar parejos · 2 de 3

Ocho palabras que vamos a usar todo el día

Concepto 1

Harness (arnés)

Todo lo que rodea al agente para convertir autonomía cruda en trabajo dirigido: comandos, gates, plantillas, verificadores. El modelo es el motor; el harness es el chasis, los frenos y el tablero. En el equipo le decimos el kit (tools/harness).

Concepto 2

SDD — Spec-Driven Development

La spec manda; el chat es desechable. Antes de una línea de código, el pedido se convierte en una especificación revisada por un humano. Lo que el agente rellene solo se marca DECISIÓN para que lo veas.

Concepto 3

RDD — Receipt-Driven Development

La revisión no es una opinión: es un recibo atado a una huella — el sha de la spec, qué tests se vieron fallar y pasar, qué gates corrieron. Si cambia un byte, el recibo se invalida. Su artefacto es el recibo (abajo).

Concepto 4

Gate (compuerta automática)

Un verificador que corre solo: ¿la clase carga? ¿quién importa a quién? ¿la columna existe en la base real? Regla de la casa: un check que devuelve cero no vale hasta verlo devolver uno.

Concepto 5

Spec (de 7 ejes)

El artefacto central: un formulario fijo de 8 preguntas — esquema, alcance, servicio dueño, contrato, retorno, tests, criterios — que sale de la entrevista. Vive en el issue de GitHub y se congela con un sha al arrancar los tests: desde ahí, cambiarla se declara, no se esconde.

Concepto 6

Recibo

La pieza RDD del flujo: el documento que /implementar (el comando que corre toda la construcción) deja al cerrar. Lo emite el instrumento (recibo.sh), no la narración del agente, y sale con un estado: APROBABLE · DEGRADADO · INCONCLUSO · FALLANDO. Viaja dentro del PR: es lo primero que lee el revisor.

Concepto 7

Mutante

Un defecto sembrado a propósito en el código para ver si los tests lo matan — el juez de los tests: si sobrevive con todo en verde, la suite no vigila nada. Así se juzga también al propio kit: casos conocidos-malos contra cada gate.

Concepto 8

Seam (costura)

El punto único y decisorio donde el feature toca la realidad y se valida por fuera: el endpoint que responde, la query contra la base viva. En la entrevista se fija con una sola pregunta — «¿cómo validamos que funciona?» — y exige un valor que solo el referente correcto produce, no que "algo aparezca".

TDD: el test existe antes que el código

Test-Driven Development: la prueba se escribe ANTES que el código, y dos corridas marcan el ritmo — ROJO (todos los tests nuevos fallan: el código no existe, y verlos fallar prueba que los tests prueban algo) y VERDE (pasan todos + los 5 gates).

1 · ROJOescribís el test desde la spec, corre, y FALLA — el código aún no existe
2 · VERDEescribís el código mínimo que lo hace pasar + corren los 5 gates
3 · TRIANGULARbuscás a propósito UN caso que rompa lo construido
4 · REFACTORordenás con la red puesta: los tests te avisan si rompés algo
// el test nace de la spec — assert de VALOR exacto public function testHydratesCarrierId(): void { $shipment = new Shipment(['carrier_id' => 41]); $this->assertSame(41, $shipment->getCarrierId()); }
$ recibo.sh rojo 12 … FAILURES! Tests: 6, Failures: 6. Error: Call to undefined method getCarrierId() rojo [ddd-php]: 6 tests, 6 vistos fallar ✓
$ recibo.sh verde 12 … (tras implementar) OK (6 tests, 14 assertions) gates: loads ✓ layers ✓ schema ✓ phpcs ✓ spec ✓ schema corre contra el esquema REAL de la base

¿Por qué rojo primero? Un test que nace en verde puede estar verificando al mock — es el anti-caso del 100% de cobertura con 4% de verdad.

¿Y si un test nuevo nace en verde igual? El recibo lo ficha en nunca_rojos y el estado sale DEGRADADO: no es un rojo — es «aprobable solo si la causa que el recibo anota te convence». El rojo no es trámite: es la prueba de vida del test, y saltárselo queda escrito, no escondido.

Triangular: los tests de la spec interrogan lo prometido; con el verde en la mano buscás el null que tu getter no espera, el borde de tu if. Rojo → defecto real, vuelve al loop.

OP 020La evidencia

Medido, no opinado

Un concepto de la base de conocimiento → una medición propia → una decisión:

1 · La base decía que la cobertura no prueba nada: hay que sembrar defectos a propósito en el código (eso es un «mutante») y ver si los tests los matan. Lo hicimos contra una suite generada por IA con 100% de cobertura — solo murió el 4%. Hoy eso vive implementado como: rojo primero y asserts de valores exactos en cada issue, y mutantes permanentes contra el propio kit — las suites mutantes*.sh le siembran casos malos a los gates (el 0/11 del punto 2). Próximo: mutar los tests de cada PR (deuda declarada — medida, aún sin implementar).

2 · Decía también que un verificador no vale hasta verlo fallar. Les dimos casos malos a nuestros propios gates: 9 de 11 violaciones pasaban el CI en verde. Por eso hoy cada gate se prueba con un caso malo antes de confiarle nada — y 0 de 11 escapan.

3 · Decía que una medición vale si se define QUÉ medir antes de correrla, y a ciegas. Re-corrimos el issue del piloto sin darle las respuestas: 2 errores cazados, 2 repetidos — y con los repetidos se corrigió el estándar.

4 · Y decía que al prompt no se le puede confiar la obediencia. Escribimos una regla textual en el prompt de agentes: 2 de 3 la citaron y la violaron igual. Por eso la verificación corre afuera del modelo: gates, spec-check, recibo.

El flujo, de una mirada

Diez piezas, tres etapas. Tocá una — el detalle aparece al lado.

Etapa 1 · decidir
Etapa 2 · construir — la corre /implementar
Etapa 3 · entregar

El flujo no está cerrado: lo que cada issue real le encuentre vuelve por la misma puerta — se anota, se mide y se corrige. Las reglas se ganaron su lugar con defectos evitados; la que no pueda mostrar el suyo, se borra.
